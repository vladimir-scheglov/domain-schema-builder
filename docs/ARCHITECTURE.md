## Высокоуровневая картина

```
┌─────────────┐       ┌─────────────┐       ┌─────────────┐
│             │       │             │       │             │
│  DSL (YAML) │──────▶│     IR      │──────▶│ YAML Schema │
│             │       │             │       │             │
└─────────────┘       └─────────────┘       └─────────────┘
      ▲                     ▲                     ▲
      │                     │                     │
   Парсер              Валидатор             Генераторы
      │                     │                     │
      └─────────────────────┴─────────────────────┘
                          │
                    ┌─────┴─────┐
                    │           │
                  CLI        Web-UI
```

**Главная идея:** DSL слишком простой для генерации, YAML-схема слишком сложная для редактирования. Между ними — **IR (Intermediate Representation)**, который балансирует: достаточно полный, чтобы из него генерировать; достаточно чистый, чтобы его проверять.

## Три слоя

### Слой 1: DSL (вход)

Компактный YAML, дружелюбный к пользователю:

- Минимум синтаксиса.
- Краткие и полные формы.
- Соглашения вместо конфигураций.
- Autogenerated ID.

Пример:

```yaml
domain: iocs.test
version: 0.0.1

entities:
  Ioc:
    label: "{type}: {value}"
    ui:
      page: true
    attributes:
      value: String
      type: enum(IocType)

enums:
  IocType: [IP, Domain, URL]

trees:
  IocTree: Ioc > Source > Incident

menus:
  - Ioc
```

### Слой 2: IR (промежуточная модель)

TypeScript-объект, максимально нормализованный:

- Все сущности, атрибуты, связи — **в массивах**.
- Все ID разрешены.
- Все автогенерируемые поля уже вычислены.
- Никаких ссылок на DSL-синтаксис.

```ts
const ir: IR = {
  domain: 'iocs.test',
  version: '0.0.1',
  entities: [
    {
      id: 'Ioc',
      label: '{type}: {value}',
      generatePage: true,
      attributes: [
        { id: 'value', dataType: 'String' },
        { id: 'type', dataType: 'IocType' },
      ],
    },
  ],
  dataTypes: [
    {
      id: 'IocType',
      kind: 'Enum',
      values: [{ id: 'IP' }, { id: 'Domain' }, { id: 'URL' }],
    },
  ],
  trees: [
    {
      id: 'IocTree',
      type: 'ordinary',
      hierarchy: { entity: 'Ioc', children: [...] },
    },
  ],
  // ... actions, views, menus, linkages
};
```

### Слой 3: YAML Schema (выход)

Полная схема домена:

- Фиксированный порядок блоков.
- 2 пробела, без комментариев.
- Пустые блоки не выводятся.
- Никаких `null` — только отсутствие ключа.

```yaml
id: iocs.test
type: domain
version: 0.0.1

entities:
  - id: Ioc
    label: "{type}: {value}"
    ui:
      page: true
    attributes: [...]

dataTypes: [...]
trees: [...]
menus: [...]
actions: [...]
views: [...]
dataRules: [...]
```

## Поток данных

```
┌──────────────────────────────────────────────────────────────┐
│  Вход: DSL-файл (YAML)                                       │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
                  ┌────────────────┐
                  │  parseDsl      │  src/dsl/parse.ts
                  │  YAML → IR     │
                  └────────┬───────┘
                           │
                           ▼
                  ┌────────────────┐
                  │  validateIr    │  src/ir/validate.ts
                  │  IR → issues   │
                  └────────┬───────┘
                           │
              ┌────────────┴────────────┐
              │                         │
        issues: ok                  issues: error
              │                         │
              ▼                         ▼
    ┌──────────────────┐       ┌──────────────────┐
    │  generateFromIr  │       │  Показать ошибки │
    │  IR → YAML       │       │  и остановиться  │
    └────────┬─────────┘       └──────────────────┘
             │
             ▼
    ┌──────────────────┐
    │  YAML Schema     │
    └──────────────────┘
```

**Точка входа** — `generateSchema(dsl: string): string` в `src/index.ts`:

```ts
export function generateSchema(dslYaml: string): string {
  const ir = parseDsl(dslYaml);
  const result = validateIr(ir);
  if (!result.ok) {
    throw new Error(formatIssues(result.issues));
  }
  return generateFromIr(ir);
}
```

## Слой 1: DSL Parser

**Файл:** `src/dsl/parse.ts`

**Задача:** превратить YAML-DSL в IR.

### Что делает парсер

**1. Разрешение кратких форм атрибутов:**

```yaml
value: String                          →  { id: 'value', dataType: 'String' }
type: enum(IocType)                    →  { id: 'type', dataType: 'IocType' }
sources: Array<Reference(IocSource)>   →  { id: 'sources', dataType: 'Array',
                                            item: { dataType: 'Reference', entity: 'IocSource' } }
```

**2. Разворачивание enum'ов:**

```yaml
enums:
  IocType: [IP, Domain]                →  dataTypes: [{ id: 'IocType', kind: 'Enum',
                                                          values: [...] }]
```

**3. Разворачивание workflow:**

```yaml
workflows:
  Status:                              →  dataTypes: [{ id: 'Status', kind: 'Workflow',
    initial: new                                                     statuses: [...],
    statuses: { new: Новый }                                         initial: 'new',
    transitions: [new -> done]                                       transitions: [...] }]
```

**4. Разворачивание деревьев:**

```yaml
trees:
  RiskTree: RiskAssessment > RiskCategory > Risk
```

↓

Парсер:

1. Находит все связи между сущностями в `ir.linkages`.
2. Ищет связь между каждой парой сущностей.
3. Если связь одна — использует её ID.
4. Если связей несколько — требует явного указания `>(linkageId)`.
5. Строит `IRTreeNode` с иерархией.

**5. Автогенерация связей:**

```yaml
links:
  Ioc:
    - n:n Incident                     →  linkages: [{ id: 'Ioc_Incident',
                                                        side1: 'Ioc', side2: 'Incident',
                                                        type: 'n_n', undirected: true,
                                                        nameFrom: {...} }]
```

**6. Чтение флагов UI:**

```yaml
entities:
  Ioc:
    ui:
      list: false                      →  entities[Ioc].generateList = false
      page: true                           entities[Ioc].generatePage = true
```

**7. Генерация меню:**

```yaml
menus: [Ioc]                           →  menus: [{ id: 'menus_iocs',
                                                     route: '/iocs',
                                                     type: 'root_group',
                                                     items: [...] }]
```

Плюс **автоматически** генерируются пункты меню для деревьев.

**8. Генерация actions:**

Для каждой сущности создаются действия по флагам:

- `actions_create<Entity>` — если `modals !== false`.
- `actions_edit<Entity>` — если `modals !== false`.
- `actions_open<Entity>Panel` — если `panel !== false`.
- `actions_open<Entity>Page` — если `page === true`.
- `actions_bulkRemove<Entity>` — если `list !== false`.

### Что парсер НЕ делает

- **Не валидирует** ссылки — это `validateIr`.
- **Не генерирует views** — это генератор `views`.
- **Не форматирует** YAML.

### Структура парсера

```ts
export function parseDsl(yaml: string): IR {
  const preprocessed = preprocessDsl(yaml);
  const raw = parseYaml(preprocessed) as RawDsl;

  const ir: IR = createEmptyIr(raw);

  parseSequences(raw, ir);
  parseEnums(raw, ir);
  parseWorkflows(raw, ir);
  parseEntities(raw, ir);       // ← читает ui:
  parseInherit(raw, ir);
  parseLinks(raw, ir);
  parseTrees(raw, ir);          // ← после links
  parseMenus(raw, ir);
  ir.actions = buildActions(ir); // ← учитывает флаги

  return ir;
}
```

### Препроцессор

`preprocessDsl` перед `parseYaml` **оборачивает** строки вида `- > ...` и `- < ...` в кавычки, потому что YAML не умеет их читать.

## Слой 2: IR

**Файлы:** `src/ir/types.ts`, `src/ir/schema.ts`, `src/ir/validate.ts`

**Задача:** нормализованная модель.

### Ключевые типы

```ts
interface IR {
  domain: string;
  version: string;
  name?: string;
  description?: string;
  author?: string;
  tags?: string[];
  status?: string;
  date?: string;

  entities: IREntity[];
  dataTypes: IRDataType[];
  sequences: IRSequence[];
  linkages: IRLinkage[];
  trees: IRTree[];
  actions: IRAction[];
  views: (IRViewEntity | IRViewList | IRViewTree)[];
  menus: IRMenu[];
  dataRules: IRDataRule[];
  medias: IRMedia[];
}

interface IREntity {
  id: string;
  name?: string;
  label?: string;
  description?: string;
  inherits?: string;
  attributes: IRAttribute[];

  // Флаги генерации UI
  generateList?: boolean;     // default: true
  generateModals?: boolean;   // default: true
  generatePanel?: boolean;    // default: true
  generatePage?: boolean;     // default: false
}
```

### Принципы IR

1. **Всё в массивах.** Даже если в DSL map.
2. **Резолвленные ссылки.** `enum(IocType)` → `dataType: 'IocType'`.
3. **Автогенерированные ID уже на месте.**
4. **Optional-поля `undefined`, а не `null`.**
5. **Флаги UI с дефолтами.** `undefined` трактуется как дефолт.

### Формат IR vs DSL

| Что | DSL | IR |
|---|---|---|
| Сущности | `entities: { Ioc: {...} }` | `entities: [ { id: 'Ioc' } ]` |
| Атрибуты | `attributes: { value: String }` | `attributes: [ { id: 'value', dataType: 'String' } ]` |
| Типы | `enum(X)`, `Reference(X)` | `dataType: 'X'` + `item` / `entity` |
| Связи | `links: { Ioc: ['n:n Incident'] }` | `linkages: [ { id, side1, side2, type, ... } ]` |
| Деревья | `trees: { RiskTree: "A > B > C" }` | `trees: [ { id, hierarchy: {...} } ]` |
| Флаги UI | `entities[].ui.list` | `entities[].generateList` |
| Меню | `menus: [Ioc]` | `menus: [ { id: 'menus_iocs', items: [...] } ]` |
| Действия | не описываются | `actions: [ { id: 'actions_createIoc', ... } ]` |
| Views | не описываются | `views: [ { id: 'viewIoc', ... } ]` |

**Views, actions, dataRules не описываются в DSL** — они **генерируются автоматически** из сущностей.

## Слой 3: Generators

**Файлы:** `src/generators/*.ts`

**Задача:** превратить IR в YAML.

### Структура генераторов

```
src/generators/
├── metadata.ts       → id, type, version, name, description, ...
├── entities.ts       → entities[] (включая ui:)
├── attributes.ts     → attributes[]
├── dataTypes.ts      → dataTypes[] (enum, workflow, table)
├── sequences.ts      → sequences[]
├── linkages.ts       → linkages[]
├── trees.ts          → trees[]
├── menus.ts          → menus[] (включая автопункты для деревьев)
├── actions.ts        → actions[] (учитывает флаги)
├── dataRules.ts      → dataRules[]
├── medias.ts         → medias[]
├── views/
│   ├── index.ts      → views[] (собирает всё)
│   ├── entity.ts     → view<Entity>
│   ├── list.ts       → lists_<entity>
│   ├── tree.ts       → tree_<TreeId>
│   ├── widgets.ts    → widgets[] (учитывает флаги)
│   ├── groups.ts     → groups[] (учитывает флаги)
│   └── cards.ts      → cards[] (panel, modal × 2, page)
└── index.ts          → generateFromIr
```

### Принципы

1. **Чистые функции.** `(IR) => YAMLNode`. Без сайд-эффектов.
2. **Один блок — один файл.**
3. **Работа с YAML AST, а не со строками.**
4. **Учёт флагов UI.** Каждый генератор проверяет `generateList` / `generateModals` / `generatePanel` / `generatePage`.
5. **Условная сериализация `ui:`.** В YAML пишутся только флаги, отличающиеся от дефолтных.

### Пример: генерация сущности с флагами

```ts
// src/generators/entities.ts
function buildEntity(e: IREntity): YAMLMap {
  const m = new YAMLMap();
  m.set('id', e.id);
  if (e.name) m.set('name', e.name);
  if (e.label) m.set('label', e.label);
  if (e.description) m.set('description', e.description);
  if (e.inherits) m.set('inherits', e.inherits);

  // Секция ui — только если есть отклонения от дефолтов
  const ui = new YAMLMap();
  let hasUi = false;

  if (e.generateList === false) { ui.set('list', false); hasUi = true; }
  if (e.generateModals === false) { ui.set('modals', false); hasUi = true; }
  if (e.generatePanel === false) { ui.set('panel', false); hasUi = true; }
  if (e.generatePage === true) { ui.set('page', true); hasUi = true; }

  if (hasUi) m.set('ui', ui);

  m.set('attributes', buildAttributes(e.attributes));
  return m;
}
```

### Пример: генератор деревьев

```ts
// src/generators/trees.ts
export function buildTrees(ir: IR): YAMLSeq {
  const seq = new YAMLSeq();
  for (const t of ir.trees) seq.add(buildTree(t));
  return seq;
}

function buildTree(t: IRTree): YAMLMap {
  const m = new YAMLMap();
  m.set('id', t.id);
  if (t.type) m.set('type', t.type);
  m.set('hierarchy', buildHierarchy(t.hierarchy));
  return m;
}

function buildHierarchy(node: IRTreeNode): YAMLMap {
  const m = new YAMLMap();
  m.set('entity', node.entity);
  if (node.children?.length) m.set('children', buildChildren(node.children));
  return m;
}
```

### Пример: генератор view для дерева

```ts
// src/generators/views/tree.ts
export function buildTreeView(t: IRTree, ir: IR): IRViewTree {
  const entityIds = collectTreeEntities(t.hierarchy);
  const treeEntities = entityIds
    .map(id => ir.entities.find(e => e.id === id))
    .filter((e): e is IREntity => e !== undefined);

  const rootEntity = treeEntities[0];
  const leafEntity = treeEntities[treeEntities.length - 1];

  return {
    id: `tree_${t.id}`,
    type: 'tree',
    tree: t.id,
    label: `Дерево ${rootEntity?.name ?? rootEntity?.id}`,
    nodeChunkSize: 20,
    variant: 'merged',
    table: leafEntity ? buildLeafTable(leafEntity, t, treeEntities) : undefined,
  };
}
```

**Что тут важно:** `filter` в таблице дерева — **массив** (по одной записи для каждой сущности иерархии), а `row_click` actions — **по одному на каждую** сущность.

### Порядок блоков в YAML

Жёстко зафиксирован в `generateFromIr`:

```ts
export function generateFromIr(ir: IR): string {
  const doc = new Document({});

  copyMetadata(doc, ir);

  if (ir.entities.length) doc.set('entities', buildEntities(ir));
  if (ir.dataTypes.length) doc.set('dataTypes', buildDataTypes(ir));
  if (ir.sequences.length) doc.set('sequences', buildSequences(ir));
  if (ir.linkages.length) doc.set('linkages', buildLinkages(ir));
  if (ir.trees.length) doc.set('trees', buildTrees(ir));
  if (ir.menus.length) doc.set('menus', buildMenus(ir));
  if (ir.actions.length) doc.set('actions', buildActions(ir));
  doc.set('views', buildAllViews(ir));

  const dataRules = buildDataRules(ir);
  if (dataRules.items.length > 0) doc.set('dataRules', dataRules);

  const medias = buildAutoMedias();
  if (medias.length) doc.set('medias', buildMedias(medias));

  return doc.toString({ lineWidth: 0, indent: 2 });
}
```

**Пустые блоки пропускаются.**

## Валидация

**Файл:** `src/ir/validate.ts`

### Что проверяется

| Код | Что проверяет |
|---|---|
| `DUPLICATE_ENTITY_ID` | Одинаковые ID сущностей |
| `DUPLICATE_ATTRIBUTE_ID` | Одинаковые ID атрибутов |
| `DUPLICATE_DATATYPE_ID` | Одинаковые ID типов |
| `UNRESOLVED_REFERENCE` | Ссылка на несуществующую сущность |
| `UNRESOLVED_DATATYPE` | Ссылка на несуществующий тип |
| `UNRESOLVED_SEQUENCE` | Ссылка на несуществующую последовательность |
| `IDENTIFIER_NO_SEQUENCE_NO_TEMPLATE` | Identifier без источника |
| `DEFAULT_NOT_ALLOWED` | default для типа, где он запрещён |
| `REFERENCE_WITHOUT_ENTITY` | Reference без указания сущности |
| `UNRESOLVED_INHERITS` | Наследование от несуществующей |
| `INHERITANCE_CYCLE` | Цикл в наследовании |
| `UNRESOLVED_LINKAGE_SIDE` | Связь на несуществующую сущность |
| `EMPTY_ENUM` | Пустое перечисление |
| `WORKFLOW_NO_STATUSES` | Workflow без статусов |
| `WORKFLOW_NO_INITIAL` | Workflow без `initial` |
| `WORKFLOW_INITIAL_UNKNOWN` | `initial` не найден |
| `WORKFLOW_TRANSITION_UNKNOWN_STATE` | Переход в несуществующий статус |
| `UNRESOLVED_TREE_ENTITY` | Сущность в дереве не найдена |
| `UNRESOLVED_TREE_LINKAGE` | Связь в дереве не найдена |
| `PREFIX_RULE_ATTR_NOT_FOUND` | Правило префикса на несуществующий атрибут |

### Формат результата

```ts
interface ValidationResult {
  ok: boolean;
  issues: ValidationIssue[];
}

interface ValidationIssue {
  level: 'error' | 'warning';
  code: string;
  message: string;
  path?: string;
}
```

**`warning` не блокирует** генерацию. Только `error`.

## CLI

**Файлы:** `src/cli.ts`, `src/cli/diff.ts`, `src/cli/hash.ts`

### Команды

```bash
dsb gen <file>           # generate
dsb gen <file> -w        # watch + diff
dsb validate <file>      # только проверка
dsb info <file>          # сводка
dsb inspect <file>       # IR в JSON
dsb init [file]          # создать шаблон
```

### Watch с diff

Ключевой модуль — `src/cli/diff.ts`.

**Как работает:**

1. После первой генерации **запоминается** предыдущая YAML.
2. При `fs.watch` — читается DSL.
3. Хэш содержимого (FNV-1a) — если не менялся, выход.
4. Если менялся — генерация.
5. Diff через `diffLines` — построчный.
6. ANSI-цвета, если stdout — TTY.

**Параметры:** `--context N`, `--no-color`, `--no-diff`, `--quiet`.

### Shebang

`src/cli.ts` начинается с `#!/usr/bin/env node`. `tsup` сохраняет её при сборке.

### UIState — модель редактора

Плоская, удобная для биндинга на формы.

```ts
interface UIState {
  domain: string;
  version: string;
  name: string;
  description: string;
```

## CodeMirror-редактор

**Ключевое решение:** используем **нативный CM6**, а не `@uiw/react-codemirror`.

**Причины:**

- Обёртка `@uiw` не применяет extensions при `basicSetup: false`.
- Обёртка пересоздаёт EditorView при каждом изменении extensions.
- Нативный CM6 — полный контроль над state и lifecycle.
- Меньше зависимостей.

### Архитектура редактора

```tsx
export function CodeMirrorEditor({ value, onChange, context, viewRef }) {
  const containerRef = useRef<HTMLDivElement>(null);
  const internalViewRef = useRef<EditorView | null>(null);
  const onChangeRef = useRef(onChange);
  const contextRef = useRef(context);

  // Обновляем refs, чтобы не пересоздавать view
  useEffect(() => {
    onChangeRef.current = onChange;
    contextRef.current = context;
  }, [onChange, context]);

  // Создание view один раз
  useEffect(() => {
    const state = EditorState.create({
      doc: value,
      extensions: [
        lineNumbers(),
        history(),
        foldGutter(),
        drawSelection(),
        yaml(),
        dslTheme,
        dslTooltip(() => contextRef.current),
        autocompletion({ override: [(ctx) => dslCompletions(contextRef.current)(ctx)] }),
        linter((view) => dslLinter(contextRef.current)(view), { delay: 400 }),
        lintGutter(),
        emmetHighlighter,
        highlightField,
        Prec.highest(keymap.of([...emmetKeymap])),
        keymap.of([...defaultKeymap, ...historyKeymap, indentWithTab]),
        EditorView.updateListener.of(update => {
          if (update.docChanged) {
            onChangeRef.current(update.state.doc.toString());
          }
        }),
      ],
    });

    const view = new EditorView({ state, parent: containerRef.current });
    internalViewRef.current = view;
    if (viewRef) viewRef.current = view;

    return () => {
      view.destroy();
      internalViewRef.current = null;
      if (viewRef) viewRef.current = null;
    };
  }, []);

  // Синхронизация value извне
  useEffect(() => {
    const view = internalViewRef.current;
    if (!view) return;
    const current = view.state.doc.toString();
    if (current !== value) {
      view.dispatch({ changes: { from: 0, to: current.length, insert: value } });
    }
  }, [value]);

  return <div ref={containerRef} style={{ height: '100%' }} />;
}
```

### Ключевые моменты

1. **`onChangeRef` и `contextRef`** — чтобы не пересоздавать view при изменении props.
2. **`useEffect([])`** — создание view один раз.
3. **`useEffect([value])`** — синхронизация извне с проверкой `current !== value`.
4. **`Prec.highest`** для Emmet-keymap — перехватывает Tab раньше `indentWithTab`.
5. **`drawSelection()`** — кастомная отрисовка выделения.

### Известные проблемы и решения

**1. Выделение мышью «отстаёт на строку»**

**Причина:** `.cm-activeLine` с `background` вместо `box-shadow: inset`.

**Решение:** всегда `box-shadow: inset` для `.cm-activeLine` и любых inline-декораций.

**2. Скрытый `<textarea>` CM6 ломается глобальными стилями**

**Причина:** глобальный CSS `input, select, textarea { padding: 6px; }` применяется к `.cm-textarea`.

**Решение:** исключить `.cm-textarea` из глобальных стилей через `:not(.cm-textarea)`.

## Семантический diff

**Файлы:** `components/dsl-editor/schema-diff.ts`, `find-position.ts`

**Задача:** показать пользователю, что изменится в схеме с момента последнего применения.

### Как работает

1. **Baseline** — схема, сгенерированная из **применённого** UIState.
2. **Current** — схема, сгенерированная из **текущего** DSL редактора.
3. **Парсинг** обеих схем в `Map<key, SchemaElement>`.
4. **Diff** — сравнение по `signature` (хеш содержимого).
5. **Результат:** список `ElementDiff` — добавленные, удалённые, изменённые.

### Парсинг схемы

```ts
export function parseSchemaElements(schema: string): Map<string, SchemaElement> {
  const elements = new Map();
  const root = parseYaml(schema);

  // entities + attributes
  for (const e of root.entities ?? []) {
    elements.set(`entity:${e.id}`, {
      kind: 'entity',
      id: e.id,
      signature: hash(JSON.stringify(e)),
      raw: e,
    });
    for (const a of e.attributes ?? []) {
      elements.set(`attribute:${e.id}.${a.id}`, {
        kind: 'attribute',
        id: a.id,
        parentId: e.id,
        signature: hash(JSON.stringify(a)),
        raw: a,
      });
    }
  }

  // linkages, dataTypes, trees, actions, views — аналогично
  return elements;
}
```

### Диагностика

```ts
export function diffSchemaElements(
  baseline: Map<string, SchemaElement>,
  current: Map<string, SchemaElement>,
): ElementDiff[] {
  const result = [];
  const allKeys = new Set([...baseline.keys(), ...current.keys()]);

  for (const key of allKeys) {
    const b = baseline.get(key);
    const c = current.get(key);

    if (b && !c) result.push({ kind: b.kind, id: b.id, change: 'removed' });
    else if (!b && c) result.push({ kind: c.kind, id: c.id, change: 'added' });
    else if (b && c && b.signature !== c.signature) {
      result.push({
        kind: c.kind,
        id: c.id,
        change: 'modified',
        fieldChanges: diffFields(b.raw, c.raw),
      });
    }
  }

  // Сортировка по типу, потом по id
  result.sort(...);
  return result;
}
```

## Горячие клавиши

**Файл:** `web/src/hooks/useHotkeys.ts`

### Как работает

Хук вешает `keydown` на `window`. При событии:

1. Проверяет фокус — если `input` / `textarea` / `contenteditable`.
2. Собирает комбо: `cmd+d`, `shift+?`, `n`.
3. Ищет в списке хоткеев.
4. **Одиночные клавиши** игнорируются в полях ввода.
5. **Комбинации с модификаторами** — работают всегда.

```ts
export function useHotkeys(hotkeys: Hotkey[], enabled = true): void {
  useEffect(() => {
    if (!enabled) return;

    const onKeyDown = (e: KeyboardEvent) => {
      const target = e.target as HTMLElement | null;
      const isInInput = target && (
        target.tagName === 'INPUT' ||
        target.tagName === 'TEXTAREA' ||
        target.isContentEditable
      );

      const combo = buildCombo(e);

      for (const hk of hotkeys) {
        if (hk.combo !== combo) continue;

        const ignoreInInput = hk.ignoreInInput ?? isSingleKey(hk.combo);
        if (isInInput && ignoreInInput) continue;

        if (hk.preventDefault !== false) e.preventDefault();
        hk.handler();
        return;
      }
    };

    window.addEventListener('keydown', onKeyDown);
    return () => window.removeEventListener('keydown', onKeyDown);
  }, [hotkeys, enabled]);
}
```

### Отключение при модалках

Хук принимает `enabled`. В `App.tsx`:

```tsx
useHotkeys(hotkeys, !paletteOpen && !hotkeysOpen && !dslEditorOpen);
```

`dslEditorOpen` поднимается через события:

```ts
// YamlPreview при открытии модалки:
window.dispatchEvent(new CustomEvent('dsb:dsl-editor-open'));

// App слушает:
window.addEventListener('dsb:dsl-editor-open', () => setDslEditorOpen(true));
```

### Палитра команд

`CommandPalette.tsx` — компонент с input и списком команд. Фильтрация по query, навигация `↑↓`, `Enter` — выполнить, `Esc` — закрыть.

## Ключевые решения

### 1. Промежуточный слой IR

**Почему:** прямое преобразование DSL → YAML было бы быстрым, но хрупким. IR изолирует форматы.

### 2. Views генерируются, а не описываются

**Почему:** 80% представлений тривиальны. Писать руками — boilerplate.

### 3. Auto-ID для связей, действий, виджетов

**Почему:** предсказуемые имена. Не нужно придумывать.

### 4. Работа с YAML через AST

**Почему:** порядок ключей, экранирование. Template strings — источник ошибок.

### 5. Нативный CM6 вместо @uiw/react-codemirror

**Почему:** обёртка не применяет extensions при `basicSetup: false`, пересоздаёт view. Полный контроль над state — проще.

### 6. Флаги UI в DSL через секцию `ui:`

**Почему:** сохраняются в файле. Работают в CLI и web-UI. Round-trip стабилен.

### 7. `box-shadow: inset` вместо `background` в темах CM6

**Почему:** `background` в inline-декорациях участвует в hit-testing и ломает выделение мышью.

### 8. Семантический diff, а не построчный

**Почему:** построчный diff схемы — это 20 строк YAML на одно изменение. Семантический — одна строка: `+ Attribute Ioc.description`.

### 9. localStorage для черновика и пресетов

**Почему:** не требует бэкенда. Работает оффлайн.

### 10. URL как способ поделиться состоянием

**Почему:** не требует сервера. Base64url в `?state=`.

### 11. Горячие клавиши через отдельный хук

**Почему:** централизованное управление. Легко отключать при модалках. Учитывает фокус в input/textarea.
